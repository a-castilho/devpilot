## Descrição e evidências da PR

## Objetivo
Criar uma única linha de integração para o **sistema DevPilot completo**, preservando o estado atual do `main` e incorporando somente trabalhos válidos que ainda estavam isolados em branches antigas.

## Base
- branch criada diretamente do `main` atual;
- não faz rollback deliberado de telas ou runtimes mais novos;
- branches antigas/superseded são reconciliadas seletivamente, nunca mescladas cegamente.

## Consolidação
### Jogo
- preserva a esteira V2 real de 7 etapas e 900 XP já existente;
- preserva os controles novos de objetivo (`Salvar e iniciar fase`, `Salvar objetivo`, `Nova partida`, `Atualizar`);
- corrige mistura de assets observada no navegador usando uma revisão única de composição do jogo;
- adiciona regressão específica da composição.

### Projetos
- mantém correções atuais de memória, modo leve/mobile, layout, Mission Control e abertura não bloqueante de `Novo projeto`;
- adiciona fallback de provisionamento: se GitHub falhar, o projeto autorizado continua cadastrado como repositório pendente, sem expor detalhe sensível.

### Execuções / resultados
- mantém respostas contextuais por run;
- adiciona contrato semântico para Análise, Execução, Validação e Recuperação;
- autocorreção resolvida em run ainda falho vira `RECOVERY_RETEST_REQUIRED`, nunca falso sucesso;
- separa Produto da Missão, Resposta contextual, Próximo passo, Evidências e Saída técnica.

### Segurança de usuários / RBAC
- `SUPER_ADMIN` passa a ser identidade raiz protegida e **não atribuível** pelo editor comum, nem por outro Super Admin;
- API `/api/users/roles` devolve somente os perfis realmente delegáveis pelo ator;
- entrada externa de role usa parser estrito: `admin` significa `ADMIN` e não reutiliza alias legado que historicamente podia representar `SUPER_ADMIN`;
- OWNER/ADMIN continuam limitados pela matriz de delegação existente;
- qualquer criação, promoção, rebaixamento ou mudança de estado envolvendo `OWNER` exige step-up com a senha atual do Super Admin;
- falha de step-up é auditada sem registrar a senha;
- contas `SUPER_ADMIN` existentes não podem ser promovidas, rebaixadas ou desativadas pelo editor geral;
- no mobile, trocar a opção do `<select>` **não executa PATCH**: a alteração só ocorre após `Salvar perfil` + confirmação explícita;
- alterações envolvendo `OWNER` usam diálogo com campo de senha mascarado;
- regressões cobrem escalada para root, alias `admin`, step-up, proteção de root e UI mobile.

### Deploy
- incorpora política R4/R5 sem substituir o cloud atual;
- homologação permanece R4 para gestão;
- produção R5 exige autorização explícita persistida;
- risco/autorização entram na auditoria e host action.

### Recursos / Android
- incorpora `resource_job` como ação aditiva;
- jobs auxiliares permitidos podem ir ao Android/Termux sob pressão de RAM;
- Codex, Docker, sudo e comandos privilegiados permanecem no notebook;
- allowlist dupla, exclusão de `.env`/segredos e fallback local;
- nenhuma credencial SSH entra nos containers.

## O que deliberadamente NÃO foi feito
Branches antigas/superseded não foram mescladas inteiras. Onde havia conflito com código posterior, foi trazida apenas a capacidade ainda ausente. Isso evita restaurar versões antigas de Projetos, Jogo, Cloud, Execuções ou autenticação.

Também não há rebaixamento automático de contas existentes: nomes/e-mails não são fonte de autorização. Qualquer correção de role persistida precisa ser explícita e auditável.
