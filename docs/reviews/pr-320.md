## Descrição e evidências da PR

## Problema fechado
As correções V34–V39 removeram travamentos de abertura, scroll, renderização e preservaram o cadastro quando o Git falha. Ainda restava um bloqueio no **submit real**: `/api/projects/provision` continuava executando GitHub de forma síncrona antes de responder. Como `create_github_repository()` usa chamadas HTTP externas e ainda prepara o starter do repositório, rede lenta/indisponível mantinha o botão de cadastro aguardando e a tela parecia travada.

## Correção V40
- o cadastro do projeto agora é **persistido primeiro**, sem qualquer chamada ao GitHub no request;
- o endpoint responde com o projeto em estado `repository_pending=true` e `repository_provision_state=queued`;
- somente depois da resposta o FastAPI executa `provision_repository_in_background`;
- o job em background abre sessão própria de banco, resolve organização/credencial e cria o repositório;
- sucesso atualiza `repository_url`, branch, `repository_pending=false` e estado `ready`;
- falha mantém o projeto cadastrado, marca estado `failed` e registra auditoria + log do motivo;
- não há mais I/O externo do GitHub no caminho crítico do botão **Criar projeto**;
- continua preservada a regra de não expor PAT/credenciais para usuários comuns;
- o Project Builder continua retornando imediatamente para Projetos após o cadastro.

## Testes
- contrato garante que `provision_project()` não contém `create_github_repository()`;
- teste funcional direto injeta uma função GitHub que explodiria se chamada no request e confirma que o cadastro retorna mesmo assim;
- confirma `BackgroundTasks` com exatamente a função de provisionamento enfileirada;
- protege estados `queued`, `failed` e `ready` do provisionamento.

## Resultado esperado
Ao tocar em **Criar projeto**, o tempo de resposta depende apenas do banco local. O GitHub pode levar segundos ou falhar sem congelar o cadastro. O projeto aparece imediatamente e o Git é finalizado em segundo plano.
