## Descrição e evidências da PR

## Causa raiz
O frontend já tratava a recuperação de GitHub como automática, mas o backend canônico podia preservar um `requires_approval=true` legado em uma tarefa de recovery. Isso deixava a etapa em `awaiting_approval` e interrompia a esteira. Além disso, a API de detalhes ainda apresentava `github_auth` como se fosse autorização humana, mesmo existindo resolução administrativa de credenciais no DevPilot.

## Correção
- normaliza `github_auth` como categoria gerenciada pelo próprio DevPilot antes de abrir gate humano;
- remove automaticamente gate de autorização GitHub obsoleto e reenfileira o recovery;
- a API de execução deixa de apresentar GitHub como autorização do usuário e informa que a recuperação automática será tentada;
- obriga a IA a esgotar alternativas automáticas seguras já autorizadas antes de considerar intervenção humana;
- informa diagnóstico, solução, evidências e limitações sem transformar aviso informativo em bloqueio;
- após recovery bem-sucedido, retesta a tarefa original; somente depois a esteira segue para a próxima etapa;
- mantém gates reais de autorização externa para categorias não gerenciadas, sem contornar permissões.

## Segurança do fluxo
A mudança não pula uma etapa com falha e não marca sucesso artificialmente. A causa deve ser reparada e a tarefa original precisa passar no reteste antes da continuação.

## Regressão
Foram adicionados/atualizados contratos para:
- classificação de falha GitHub como recuperação automática;
- normalização de diagnóstico GitHub legado com `requires_authorization=true`;
- reparo de gate GitHub legado;
- preservação de autorização externa real;
- contrato automation-first do prompt de recuperação;
- mensagem ao usuário sem expor erro Git bruto.

A branch foi atualizada sobre o `main` mais recente para não atropelar alterações paralelas.
