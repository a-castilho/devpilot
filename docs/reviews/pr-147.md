## Descrição e evidências da PR

## Problema
O gateway de provedores classificava respostas HTTP 401 e 403 da API oficial com a mesma mensagem: `API key rejeitada pelo provedor.` Isso impede diagnosticar se a credencial está inválida/revogada ou se uma chave restrita não tem acesso ao catálogo de modelos.

## Correção
- classifica falhas de catálogo com `code` e `upstream_status` seguros;
- diferencia 401 (`authentication_failed`) de 403 (`catalog_forbidden`);
- preserva tratamento separado para 429, indisponibilidade, catálogo inválido e demais HTTP errors;
- mantém o corpo de erro do provedor e a API key fora das mensagens/auditoria;
- adiciona regressões específicas para 401, 403 e 429;
- atualiza a regressão existente de autenticação;
- documenta em `docs/credentials-lifecycle.md` o padrão provider-agnostic de persistência e revalidação de credenciais.

## Comportamento esperado
Ao repetir o cadastro, a UI passa a informar a causa real sem expor segredo:
- 401: chave não autenticada; conferir chave/projeto/organização;
- 403: acesso ao catálogo negado; revisar permissões da chave/projeto.

## Padrão de ciclo de vida documentado
A credencial deve ser cadastrada uma vez e permanecer persistida com segurança. O padrão formaliza três estados:
- `active`: validação confirmada;
- `pending_validation`: credencial persistida, mas validação inconclusiva por causa transitória;
- `invalid`: falha conclusiva de autenticação/permissão ou formato inválido.

Falhas transitórias como timeout, rede, 429 ou 5xx não devem apagar a credencial nem exigir recadastro. O segredo nunca retorna ao cliente e não pode aparecer em logs, auditoria ou corpo bruto de erro.

## Escopo
Este PR implementa a classificação segura das falhas e registra o contrato arquitetural. A adoção integral dos estados de ciclo de vida na persistência/revalidação fica explicitamente definida como evolução seguinte; não está sendo simulada como já implementada neste PR.
